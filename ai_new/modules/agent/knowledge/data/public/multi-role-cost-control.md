# 多角色工单的成本与收敛规则

来源：T-20261127-0002（工单号一键复制）真实自然语言跑，2026-11-27。

## 结论

一个小需求烧到约 20 元，不是模型单价问题，是编排预算失控：

- 单轮 ReAct 上限 60 步，工具输出 20000 字符；一个角色一轮就能把几十万 token 反复送上游。
- PM 的执行/验收阶段工具只有 ticket_read/note/todo，**没有 role_task/role_spawn**，角色返工时 PM 实际上什么都做不了，只能反复等或重复派。
- 同一角色会话返工被 `bindrole` 重复 append，工单里出现两条同 session 记录，状态机与前端计数重复。
- 角色提示词没有硬预算，开发在全仓扫 spec/门禁/夹具，测试停在“设计阶段无 shell”，评审没被拉起。
- `auto_retrospective=false` 且 PM 没有 `knowledge_write`，结单后不可能沉淀知识。

## 固定规则

1. 单轮最多 30 步，工具输出 6000 字符；超过即落盘，不把大输出反复送模型。
2. 一个工单默认最多 3 个角色、2 轮返工；同角色同目标只 role_task，不重复 role_spawn。
3. PM 执行阶段必须持有 role_spawn/role_task/artifact_read/prompt_read/prompt_patch/knowledge_write；角色卡住先改提示词再重派。
4. 角色任务书必须写硬预算：最多读 8 个文件、6 条定位命令、30 步内落码或报 blocked。
5. 测试 design→run 必须进下一轮用 shell；QA 未执行不得进评审；评审空产物直接 blocked。
6. 结单后 PM 写一条 public/project 知识，再关单；没有可沉淀要显式写“无需沉淀”。

## 验收口径

- 看工单消息条数、单轮步数、token 使用和结单结论，不只看“有没有回复”。
- 返工次数 >2 或同角色出现两条会话记录，视为编排缺陷。
- 角色长时间只读不写，视为提示词/任务书缺陷，不是角色“不听话”。
