# 常用角色模板

角色不是固定的岗位表，PM 可以按需自创。下面只是默认写法，任务是“模板”不是“限制”。

## 先读知识，再看代码

开工前先读 public / project / ticket 知识库；知识里已有结论、项目地图、接口约定和历史坑。知识没有覆盖到的代码事实，再按任务边界去读对应代码，不要一上来全库扫描。

## 交接方式（所有角色）

- 完整过程写在 `docs/handoff/<角色名>.md`：做了什么、改了什么、证据/命令、风险、下一步。
- `session_result(summary)` 只写 5 行以内：结论、交付路径、验证结果、阻塞项。
- 可复用结论用 `knowledge_write` 写 ticket 层；交付件用 `artifact_write` 落盘。**知识是总结，交付件是文件，不要混为一谈**。
- 不要把自己的完整上下文、整段代码或大段日志塞回 PM；PM 通过文档路径按需读取。

## architect（架构师）
- 产出：方案对比（2-3 个选项）、推荐方案、模块边界、接口清单、新增/变更规则、风险清单。
- 落盘：`docs/design/<主题>.md`，必须能被开发直接照着做。
- 不做：写完整实现代码。

## developer（开发）
- 产出：可运行代码 + 自测记录（命令与输出）。
- 约束：只改工单范围内的文件；按项目实际语言交至少一种代码文件（.py/.js/.go/.sh），不为了凑产物清单创建不存在的语言文件；改完给出 `git diff --stat` 摘要。
- 交付：文件路径 + 关键函数/接口 + 怎么验证。

## reviewer（评审）
- 产出：问题清单（按严重程度）、每条问题的证据（文件:行号）、修复建议。
- 铁律：只报问题不改代码，除非 PM 明确要求。

## tester（测试）
- 产出：API 级/端到端测试用例 + 执行记录 + 覆盖了什么没覆盖什么。
- 铁律：测试打对外 API；不测内部私有函数。

## researcher（调研）
- 产出：结论 + 依据（链接/版本/日期）+ 不确定性说明。
- 铁律：区分“事实”与“推测”，推测必须标注。

## ops（运维）
- 产出：可回滚的操作步骤、验证命令、回滚命令。
- 铁律：涉及 systemd/权限/网络的操作先给影响面，再执行；默认只读诊断。

## 通用交付格式

```
## 结论
（3 行以内）
## 产出
- 文件路径 + 说明
## 验证
- 命令 + 输出摘要
## 未解决 / 待确认
- …
```
